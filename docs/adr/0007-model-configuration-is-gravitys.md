# 0007 — The model configuration is gravity's own, and it lives in the field

> **Languages:** [English](0007-model-configuration-is-gravitys.md) (primary) · [中文](0007-model-configuration-is-gravitys.zh-CN.md)

**Status:** Accepted (2026-10-30). A ruling on ownership and on the place of the facts; the pool's selection rule stays open.
**Date:** 2026-10-30

## Context

A turn needs five facts that belong to no request: the memory store's URL, the LLM endpoint, the model name, the name of the env var holding the key, and the scope k10r's memory doors are addressed in. Today prism assembles all of them (`crates/prism/src/turns.rs`'s `TurnConfig::from_env`) and hands them to the booth as call arguments.

That is the wrong repository. Prism is a generic gateway: it authenticates a connection, parses what the page sent, and puts an event on the plane. Which model answers, at which endpoint, with which credential NAME, is not a gateway fact — it is the booth's own configuration, and a gateway that holds it turns "change the model" into "redeploy the gateway" and puts a second component's business vocabulary inside the component that is supposed to know nothing about it.

So the facts move to gravity. But a fact needs a place, and gravity has none: the turn guest declares no storage. The mechanism is already there — `Engine::register` introspects a script booth, persists the definition (schema included) and allocates the type's ns on the way, and the realm builds that type's `ctx.store` plan from the persisted copy — but nothing in this tree has used it: the shape is exercised by the steel-carrier fixtures, and no induction guest has declared a `storage` block yet. A Rust-body booth can never have one (a compiled handler is not persistable), which is why the test collectors print `no storage ns`. The field is where it belongs, and the field is aura: the realm's embedded store, reached from a guest through the remote-store arm that is already on the ctx (`PutDocument` / `GetDocument` / `PutFields` / `GetFields` / `Scan` / `DeleteDocument`), with rows that outlive every process and are one read away inside the turn.

Custody is unchanged and it constrains the shape: the KEY VALUE never leaves the process environment. A row may name the env var (`key_env`); it may never carry the key.

## Decision

**RULING — gravity owns its model configuration, and it is stored as rows in the field (aura, through the remote store), managed through an interface gravity provides. Prism passes only what the page knows.**

1. **Prism keeps no model vocabulary.** No endpoint, no model name, no `key_env`, no memory scope: prism's turn implementation is deleted, and a page's submit carries what the page can know — the conversation it is in, the text, and the output shape it wants back. A deployment fact that only the booth reads belongs in the booth.

2. **The facts are rows in gravity's own collection, read by the turn at its start.** One settings document (store URL, memory scope, the default model) plus a model table addressed by alias. The read is local and cheap — the store is the engine's, not a network hop — and it happens per turn because a turn is where the choice is applied.

3. **Every model row is a full recipe, so a pool is the same table.** `{alias, endpoint, model, key_env, weight, enabled, affinity}`: one row is the simple deployment (alias `default`, weight 1), many rows are the pooled one. The affinity key is the SESSION: one conversation stays on one model, because that is the unit a prompt cache is built around. How a pool picks among eligible rows (weight, round-robin, ties) is a later mode and NOT fixed here; its rows are, because a pool that lives somewhere else becomes a second source of truth the moment it exists.

4. **The management face is a VIEW, like everything else the application shows.** gravity answers `ui:gravity-model` by emitting frames that expand a model-management layout; the buttons inside it emit ordinary events, gravity performs them, and the page asks for the screen again. This is the stack's general interaction pattern rather than a gravity invention — prism `docs/MODELING.md` states the model: the venue pushes a layout, a page's uplink and downlink carry NO prefix (prism adds `ui:` on the way in and strips it on the way out, ADR-0017), every action is an event, and an AI can drive the same events with no second surface. It is deliberately NOT an admin HTTP verb, a config file, or an environment variable: one home, and it is a home the user can see. The same holds for storage itself — several applications on one field each get their own ns, so an application declares its collections once and stops thinking about where rows live.

   The screen is ONE root, not rows appended to a list. `ui:gravity-model` is reached by subscription (`on_as("ui:gravity-model", "device", "screen")`, auth `true` like the rest), and it answers with `create` — the same root the shell draws on `ui:connect` — carrying a form per table (`models` and `settings`) as children of its body case (`frame_root(forms)`). Asking twice replaces the root and leaves one screen: a configuration screen is the deployment's whole face, not a stream, and its two fixed forms carry no row id for `append` to key on (keying them would make the second answer a duplicate the renderer rejects, ADR-0005's rule). The caller names no slot — the booth owns what its own screen looks like, and a click could never name one anyway.

   A form says which row it writes with FIELDS, not with its destination: `collection` and `id` ride as `text` nodes bound as form fields (`{kind: "field", field: "collection", default: "models"}`), because fluxen's form collects every `field`-bound child and sends `{field: {data, payload}}`, and a text node has no input to type into — so the pair travels with the submit and cannot be retyped. A hidden field would be nicer; the model has none, and adding one to fluxen to serve one screen is the wrong direction. Each form submits to the BARE name `gravity-model.save`: a page's uplink carries no marker, and the venue adds `ui:` on the way in.

   The act behind that name is `ui:gravity-model.save`, declared with the turn (`on_as` in `gravity_booth::register`, handler `save` in the guest) and gated by the same auth declaration prism reads (`{"ui:gravity-model.save": true}`). Its payload is one row — `{collection: "settings"|"models", id, doc}` — written into this type's ns, and it also accepts the form's shape, `{field: {data, payload}}`, unwrapped in one place before validation, where numbers are coerced too (an input's text is a string, a `number` input a float, and the declared width is 8 bytes — `"37"` does not encode). A collection the deployment cannot configure, or a document missing a key the turn reads, is refused by name. Both answers are EVENTS — `ui:gravity-model.saved`, and `ui:gravity-model.error` with the missing keys listed — because a handler reached by an event has nothing to return to (ADR-0009 §4).

   An unconfigured deployment still draws: the screen reads rows with a plain `get_document`, not `read_settings` (which refuses by name because a TURN must not run on half a deployment), and empty rows give empty forms — the only state from which a deployment can be configured at all.

   A refusal is said twice, because it has two readers. A program reads the event; a person reads the screen, and a non-list payload injected into a slot nobody binds is invisible — "refused" and "nothing happened" look the same on the page. The screen therefore carries a notice area: a float holding a rack bound to the fixed slot `notice`, above the forms, taking no room while empty, and a refusal appends the same detail there as a row. The frame carries no lifecycle — how long a line stays, how it enters, whether it rotates and what holds it still are the renderer's `view` (fluxen ADR 0024), following the ruling that the deployment says the message and the UI decides how it is shown. The only vocabulary this adds on the wire is the event `ui:gravity-model.notice` and the slot name `notice`.

5. **A fresh deployment has no rows, and that is a named error.** The turn fails loudly, naming the document and the key that is missing, instead of falling back to an environment variable. A fallback is a second home by another name.

6. **Custody is untouched.** Rows carry `key_env` (a name); the value lives in the turn process's environment, read when a stream opens, through that name. No configuration surface — stored, argued, or served — ever carries the key.

## Considered and rejected

- **Prism injects the facts into the envelope when it routes the event** (the version this record replaces). It keeps prism's code thin in line count and wrong in kind: a gateway that carries the booth's endpoint is a gateway redeployed whenever a model changes, and the injection point is the one place where nobody would look for it.
- **Environment variables only.** No interface for the user, no pool, no per-deployment override without a redeploy, and no way to answer "which model is answering right now" other than reading a process's environment.
- **A configuration file inside gravity's deployment.** A file and a store disagree the first time either is edited; the store is already the mechanism the booth reads and writes as a citizen.
- **k10r as the home.** k10r is the memory substrate — the session log, the fact graph, tasks. A model recipe is booth deployment state: it is read before a turn has any memory to consult, it is not recalled by similarity, and putting it behind the HTTP hop would make the turn's own start depend on a service the turn is about to call anyway.
- **Letting the page choose the model.** The page is a renderer; a model choice is a capability and a cost decision. If a user must choose per conversation, that is a row plus an affinity rule, not a field in an uplink.

## Consequences

- **Prism's `turns.rs` goes with the rest of its turn code** (`TurnConfig`, the slot counter, `run_turn`), and the layout's `turn.submit` becomes an ordinary event on the plane. What prism keeps is venue infrastructure: its own node manifest (`mounts`) and the plane itself.
- **The turn's args shrink to what the page knows** — conversation, text, output shape. Deployment facts stop travelling per call, so a caller can no longer forget one and get a different behaviour for the same input.
- **Gravity's booth declares `.storage(...)` beside its `.auth(...)`, and that is the whole registration work** — PROVEN 2026-10-30: the induction carrier's schema block reaches the realm as a plan on the first try (`.storage()` takes the COLLECTIONS map, since the schema nests it under `storage` already; wrapping it again parses as "this type declares nothing"). `Engine::register` introspects the guest, persists the schema (allocating the type's ns on the way), and the realm builds the plan from the persisted copy, so it survives a restart.
- **A TYPE OWNS ONE NS, so a collection inside it needs a key DISCRIMINATOR** (measured, aura ADR-0026's shape): `store_exec` builds every collection against `plan.ns` and encodes only the declared key fields, so two collections with the same `id` write the SAME row — the second write silently replaced the first, and the read returned one collection's fields under the other's name. Gravity's tables therefore key on `[kind, id]` (`settings` = 1, `models` = 2). Anyone adding a third collection must pick a new kind, and anyone reaching for a second collection in another booth should assume the same trap.
- **A pool becomes a table edit, not a deploy.** Weight and affinity are data; the selection rule is code, and it is gravity's.
- **The CLI reads the DATA protocol, and the two modes are the caller's choice.** `protocol: fluxen` draws (frames, slots the caller names); a delta consumer names the event its chunks are spoken as, and the venue strips the `ui:` marker on the way down (prism ADR-0017), so the CLI sees the plain names it already speaks. Neither mode is a second implementation: one turn, two renderings (ADR-0009).
- **The turn addresses a DEVICE, never a channel.** The transport knows devices and users (prism ADR-0018); a channel is an application's business, and this application has none — no groups, and two users do not talk to each other. A turn answers the device that asked, and a booth's own emit names no `sender`, because the venue drops a sender from its own event's fan-out.
- **Verified end to end:** `turn_booth::the_screen_draws_the_forms_that_write_the_rows` — empty forms → two frames submitting the save event → a form-shaped click writes both rows, numbers included → the screen re-draws with the saved values → a turn runs on them — plus `scripts/smoke-venue.sh`, which asks for the screen over the REAL venue and asserts the two forms and their destination before configuring anything from outside, and a browser run over CDP (system chromium): `manage` → two prefilled forms → a new alias typed → save → ask again → the same two forms with the new value and no third pair.
- **Open:** the pool's selection rule (weights, ties).
