# 0011 — 组合是图：控制边、数据边、一份 run 文档

> **语言：** [English](0011-composition-is-a-graph.md)（主） · [中文](0011-composition-is-a-graph.zh-CN.md)

**状态：** Accepted（2026-11-16）。**取代 ADR-0005**（skill 的体是代码）。**修订 ADR-0003**：§1 的判据与 §2 的胶水载具规则被替换；§3（进度是数据）与 §5（执行历史不改写拓扑）继续成立，并且在这个形态里更重要。
**日期：** 2026-11-16

## 背景

ADR-0005 裁决多步 skill 的组合是一段用已有语言写的脚本，两条理由：自造步骤语言最后会变成一个手写求值器；JSON 只能表达一个固定序列。ADR-0003 §1 从另一侧给出同一个结论：代码是图灵完全的，而流程引擎的上限是它自己的词汇表，何况模型写代码比写流程 DSL 更好。

此后出现了两条这两份记录都没有看见的需求。

第一条是**会等待人类的步骤**。一段停在表单上的脚本必须自己握住续延，而常驻 guest 的会话键是对话（ADR-0004 §3）——于是这个等待的代价是每个对话一份常驻解释器，并且随进程去死。改成持久化，就是把解释器的局部变量序列化。

第二条是**必须可 fork、可恢复、可重放、可审计的 run**。解释器的局部变量没有地址：\"从第 3 步换个参数重跑\"没有机制，\"第 3 步到底收到了什么\"除了翻日志没有答案。

一旦这两条成为需求，ADR-0003 §1 的论证就反过来了。无界的表达力，在一个必须可审计、成本可上界、可画图、可静态检查的执行器里不是优点——一个程序什么都能做的形态，根本无从检查。ADR-0005 称为局限的那个东西，是契约。

## 裁决

**RULING——skill 的组合是节点里的一张图，代码是叶子，每一次执行是一份文档。**

### 1. 判据是协议 vs 语言，不是表达力

一个形态，如果其中的程序能表达无界计算，它就是**语言**；如果不能，它就是**协议**。协议的上限是前提，不是缺陷：没有上限就没有穷举，没有穷举就没有审计、没有静态检查、没有成本上界。ADR-0003 §1 的判据（图灵完全是一种优势）被这一条替换。

### 2. 步骤与控制边住在 skill 节点里；没有胶水脚本这一层

`steps` 成为定义：每个步骤声明 `id`、`kind` 以及它自己的部件。组合只有一种表达。需要真正逻辑的组合，把逻辑放进 `code` 步骤——步骤是一条可复用、被计数、可审查的行，而一段内联地调兄弟步骤的脚本不是。

### 3. 三个原语，按"这一步什么时候完成"分

`call`（执行体——mount 上的一条 code row，或一个可寻址的 target——给出结果，结果到达即完成）、`request`（一个声明式请求发出去，**拿到数据之前这一步不完成**：这是 run 可以挂起几天的唯一来源）、`send`（消息单向发出，送达即完成，输出没人读）。交互是一个**节点**，不是脚本 API：节点自带一张**表单**——封闭的数据定义，`title?` / `description?` / `fields[]`，字段类型是 `bool|string|integer|number|choice`——并自己去申请 UI 协议；派发方发出请求，答案落在这一步的输出上。审批不是一种原语：它就是表单只有一个 `bool` 字段的 request。request 还带一个可选的不透明 `resource`（谁来回答：URL、设备、队列、人），那是预留给 oracle 的槽——解析它的宿主就跳过了提示。

步骤的脚本拿不到 ctx，也拿不到 run 文档的句柄。它是从输入文档到输出文档的纯函数。正是这份纯粹，让缓存、沙箱、fork 与重放成立；一段随时能伸手取东西的脚本，这四样一样也没有。

### 4. 数据边是派生的，控制边是声明的

数据边来自 `inputs` 的引用（§8），不携带身份：没有标签、没有预算、没有名字。它服务于渲染第二层、fork 的影响分析、以及 §6 背后的可达性检查。控制边写在 `out_edges` 里，只携带边能说的三件事：`when`（§7）、`budget`（回边必填）、以及同一个 selector 至多一条 fallback。

两者在 ready 判定处汇合：控制边决定哪些步骤被**激活**，数据边决定这一步**能不能跑**。

### 5. 条件成立的出边全部激活

一个步骤完成之后，所有条件成立的出边都被激活——不是第一条，也不是其中一条。于是 switch 与并行是**形状**而不是模式：一个取值挂一条边是 switch，挂多条是扇出；节点上不存在一个可能与图矛盾的 `mode` 字段。

fallback（`*`）只在该 selector 上没有任何带标签的边命中时触发。这是整个引擎里唯一一处一条边要看兄弟边的地方，在这里写成规则，而不是留给读者猜。

### 6. ready 是数据问题，不是入边计数

一个步骤 ready，当且仅当它 `inputs` 里每个 required 引用都可解析；optional 引用可以缺失，以\"缺失\"的形态交给代码自己处理。

- 编译期：required 引用必须至少有一个**无条件**生产者（不跨条件边即可到达的步骤），否则计划被拒。
- 运行期：ready 集为空但仍有 pending 步骤，整份 run 以 `stalled` 收尾，并报出没有任何东西喂的引用。

这就是令牌模型的汇合问题在这里没有对应物的原因。令牌模型数\"来了几个\"，所以必须知道\"本该来几个\"；数据模型只问\"我的输入在不在\"，于是汇合等的是值、永远不是边——也不存在一个会被搞错的\"本该\"。

### 7. 条件是 selector 的相等

判断步骤只吐**一个**键，值是它自己词表里的一个字符串；边测试 `selector == value`，或者作为 fallback `*`。没有否定、没有合取、没有比较、没有算术、没有表达式文法：依赖多个事实的判断，在发 selector 的那段代码里把值算出来。

白送两个性质：互斥是结构性的（一个键只有一个值，所以同一判断不可能同时走两条支），多路分支不需要级联一串判断节点。

### 8. `inputs` 就是读取声明

步骤的 `inputs` 把 code row 自己的形参名映射到引用（`$.step_2.paths`）或字面量。这些引用**就是**读取——没有另一个 `reads` 字段可以和它漂移，派生的数据边是同一份清单的投影。

返回值就是输出，存在步骤自己的 id 下：单赋值，一个步骤一个键，多个值装进一个对象（`$.step_3.paths`）。

### 9. run 文档是追加日志

每次遍历追加一条 `{step, pass, output}`；读取解析到最新的那一次。回边永远不覆盖某一次遍历，于是第 3 圈收到的东西活过了第 4 圈，重放时比较的是输入而不是重建输入。

### 10. fork 是一行记录，复用的工作被标记

一次 fork 是 `{parent_run, 参数变更, reused}`。重跑集是被改参数的数据依赖传递闭包；任何被复用的输出都在记录里带上父 run 的 id。旧的上游配新的下游是允许的，但永远可见——绝不静默。

### 11. 审批绑定在被批准的东西上，拒绝是一条出边

审批判决是 approve / reject(reason) / modify(parameters)，不是布尔；并且绑定在被批对象的内容摘要上：摘要变了之后重新规划，只作废那一条审批，别的都不动。拒绝是一条指向 revise 步骤的出边，输入是被拒项、它们的理由和计划版本——于是已批准的子集连同它的审批活过这次修订，不被重新审一遍。

### 12. 执行历史永不改写拓扑

ADR-0003 §5 原样成立，并且在这个形态里更重要：图是定义，run 是一行记录，任何执行路径都不改步骤、不改边。反复出现的组合以提案形式申请提升（k10r ADR-0016），绝不自我应用。

### 13. 一个叶子 crate：调度器与校验器

`ready(plan, run)`、`advance(plan, run, outcome)`、`validate(plan)`。没有 I/O、没有图类型、没有 tokio、没有 aura：plan IR 是普通的自有结构，从 skill 节点编译出来，按它所编译子图的内容哈希缓存。它是一个纯折叠，一张表就是它的全部测试。

其余一切都归别处——定时器、重试、派发与等待归派发方（gravity）；持久化与 run 文档归 store（k10r）；投递归事件面（aura）。一个把这些收进自己的调度器，是一个再也无法从文档恢复的服务。

### 14. Aura 是投递面，不是对立的形态

图说哪些步骤有资格，aura 说哪个实例收到这份工作。两者正交，而且是刻意正交的：引擎永远不是阻塞解释器。每次推进是一次调用——算、派发能跑的、追加、返回。等人中的 run 就是 pending；进程可以去死，下一次推进从文档恢复。

## 考虑过并否掉

- **两种节点模式，`parallel` 与 `branch`。** 模式是定义，可能与图矛盾；一个取值挂几条边不会。
- **N 个布尔加有序边、先命中先赢。** 顺序变成活在一个集合里的语义而不是定义里的语义，两个人读同一份计划会读出两种行为，互斥退化成作者要自己守的纪律。单个 selector 让互斥成为结构性事实，并且不需要顺序。
- **带否定的布尔条件。** 否定是表达式文法的入口——`!a` 之后就是 `a or b`，再之后是比较。一个 selector 取值覆盖了否定原本要解决的问题。
- **基于令牌的汇合（AND/OR 网关形态）。** 数到达数的汇合还必须知道本该到几个，这件事静态检查定不了，运行期也只能靠可达性游戏去猜。数据驱动的 ready 把这个问句删掉了。
- **在脚本里保留 ctx 桥。** 正是它让脚本不纯：随时能读任何东西，于是不可缓存、不可 fork、不可重放、不可上界——而这四样正是这个形态存在的理由。
- **为\"简单\"的 skill 在图之外保留胶水脚本层。** 两个组合者，其中一个是审计漏洞，而且选哪个会取决于作者而不是需求。
- **一个拥有定时器和重试的独立执行服务。** 它重复 aura 的投递，并且放弃可恢复性：服务内存里的定时器活不过重启，文档可以。

## 后果

- **`invoke_skill` 换形态。** 模型不再指名下一步：它启动一个 run（或推进一个 run），由调度器决定跑什么。一次调用一步不再是走法。
- **组合不再要求 `induction` 载具。** ADR-0003 §2 曾要求组合出来的操作骑在带 ctx 桥的 mount 上。一个步骤是一次调用——参数进、返回值出——所以它可以骑一次性 `exec` 载具，组合路径上没有任何东西需要通道。
- **ADR-0005 被取代，本记录同样不授权任何 DSL。** 它授权的是一套封闭的节点种类词表加三个边属性——一个协议，用 §1 的判据可以检验。
- **k10r ADR-0015 §3 的 `steps` 不再是过渡形状**：它就是定义，仍然是 store 不解析的 TEXT JSON。
- **迭代与循环都上界。** 没有 map/iterate 节点：扇出宽度来自数据，并由声明的上限封顶，所以一次 run 的最坏步骤数可算。循环是带回边预算的回边，没有预算的回边被拒。
- **计划可画图，而且图是定义。** 从计划画出来的流程是本存储边的投影，不是对执行轨迹的猜测。
- **有两样东西必须在本仓之外设计**：`ask` / `approve` 节点所申请的 UI 协议（prism / fluxen 侧，本仓未核实），以及让这种节点可以在无界面环境下执行的满足路径。

## 待定

- **run 文档住在哪。** k10r ADR-0021 裁决任务是有应用状态的顶点；run 文档是同一类东西，所以最可能的家是那个命名空间而不是新的行种类。本记录不定。
- **编译后的计划缓存在哪**——k10r（图的拥有者）还是 gravity（执行者）。内容哈希在两边都让它成为缓存而不是第二份真相。
- **只由循环体喂养的引用，校验规则怎么写。** 循环里的步骤读的是本轮之前由体产出的输出；\"无条件生产者\"这条必须写到：保证至少跑一圈的循环合法，可能一圈都不进的循环不合法。
- **`ask` 与 `approve` 的 UI 协议形状**，以及没人回答时无人值守的 run 怎么办：以 `needs_input` 让这一步失败，还是让整份 run 失败。
