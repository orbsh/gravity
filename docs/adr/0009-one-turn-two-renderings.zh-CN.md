# 0009 — 一次 turn，两种渲染：给表面的是帧，给程序的是裸文本

> **语言：** [English](0009-one-turn-two-renderings.md)（主） · [中文](0009-one-turn-two-renderings.zh-CN.md)

**状态：** 已接受（2026-10-30）。它固定 turn 的输出如何面向两类消费者；它不新增第二次 turn。
**日期：** 2026-10-30

## 背景

一次 turn 一个 chunk 一个 chunk 地产生文本，而这些文本的消费者并不相同。Web 表面负责画：它要的是针对自己声明的槽位的 Accrete 操作，因为页面上别的一切都是这种操作，而它没有理由去解析模型的输出格式。程序（CLI）负责读：它要的就是 delta 本身、按顺序，拿到之后怎么用是它自己的事。

两种诱人的形状都是错的。两套 turn 实现——一套「给 UI」、一套「给 CLI」——等于把 append 规则、工具循环和旁路逻辑放在两个地方各自漂移。把 UI 形状的输出丢给程序去解析，则是把画图的词汇塞进一个不画图的消费者：程序得先看懂 `patch /bind/value/default` 才读得出一句话。

turn 的行为不随受众改变：取投影、跑模型与工具、append 这一问一答。变的只是离开它的东西的形状。

## 决定

**裁决 —— turn 只有一份实现、两种渲染，由调用参数（`protocol`）选择。**

1. **`fluxen` 画，raw 说。** `protocol: "fluxen"` 让每个 chunk 变成一批针对调用方声明槽位的操作；默认（`data`）让每个 chunk 变成调用方命名事件上的一个裸 delta。同一套循环、同一套 append、同一条失败规则。

2. **两种模式下名字都归调用方。** 槽位名（`slots.rack`、`slots.text`）来自调用方——不是因为 gravity 恰好没有布局，而是因为布局属于**应用**，而只有握着布局的一方才能判断它发出的帧对不对：一个槽位名就是一句「我的表面在这里读」，这句话只能对着布局被验证。槽位随布局走，不随执行器走；gravity 往它被告知的位置画。数据模式的事件名（`event`）同样来自调用方，因为 gravity 不自造场馆词汇。要画却不给槽位、或要数据却不说事件名的调用方会被按名字拒绝——gravity 两样都不替它编。

3. **两种渲染并不一一对应，这一点明说。** view 模式承载的是答案的**画法**：提问气泡、文本区域、读它的气泡，然后每个 chunk 一次 patch。data 模式承载的是**文本**：每个 chunk 一个 delta，与舞台无关。想从 view turn 拿到文本的消费者去读 patch；没有任何东西会同时发出两种形状。

4. **结束语走 chunks 走过的那条线。** 画图的 turn 以 `view:turn.done` / `view:turn.error` 收尾（页面的提交是一次 emit，它没有可读的答案）；数据调用方读 handler 的终止值，即 `{reply}`。两种模式都不自造第二个终止信号。

5. **两个客户端都是客户端。** Web 表面（渲染腿）用帧；CLI 用裸 delta。谁都不特殊：CLI 不是第二个执行器，页面也不是第二个模型驱动者——一次 turn 就是同一个摊位调用，经同一个场馆抵达。场馆下行会剥掉 `view:` 标记（prism ADR-0017），于是程序看到的是它本来就在说的裸名字，而平面上仍然带标记。

6. **被取消或失败的 turn 渲染方式不变。** 输出模式不改变 append 规则（ADR-0012：失败的 turn 不 append），也不改变取消的边界（ADR-0008）。

## 已考虑并否决

- **两套 turn 实现（一套 UI、一套 CLI）。** 同一批规则两个家；第二个会烂掉，而分歧会以「CLI 的回答和 web 的不一样」出现。
- **在一个信封里同时发两种形状。** 消费者于是必须知道该忽略哪一半，信封上长出没人要的字段。
- **让 CLI 读帧再抽文本。** 它得先学会画图词汇才能读出一句话——把渲染器的知识塞进自动化客户端。
- **让页面解析 delta。** 同一个错误的反向镜像：渲染器学会模型的传输格式，还得把它已有的流式 UI 重新实现一遍。
- **用一个 `--json` 开关重塑帧。** 重塑是消费者的事；摊位说明它画了什么、说了什么，客户端自己决定。

## 后果

- **两种模式可以由同一个 fixture 覆盖**，摊位测试就是这么做的：数据模式收集 `{"delta": …}` 载荷并拼出回答，view 模式收集操作批次并断言 patch 之前的舞台。新的消费者模式是对本记录的一次测试，而不是一次新的 turn。
- **调用方不会再在 turn 中途撞上另一种形状**：模式由 args 固定，未知的 `protocol` 值是点名该参数的 error value，而不是静默回落。
- **CLI 的退出码契约（ADR-0002）不变**——裸模式本来就是它想要的；它只是不再由别人代产。
- **开放项：** 一次 turn 是否应该携带混合渲染（文本 + 工具轮的一条进度帧）。今天不带：工具结果是模型的，不是消费者的。

## Update — 2026-10-31：经事件投递的提交读不到返回值，所以它的结束要说出来

数据模式的终止信号原本是"handler 的返回值"，而这只对 INVOKE 的调用方成立。页面和 CLI 真正走的是
事件：`ui:turn.submit` 经订阅到达摊位，而投递会丢弃函数体的返回值——于是数据模式的消费者看到它的
`delta`，然后就永远没有下文。

在整条栈上实测（prism 的 `turn_invoke_skill`，它现在通过场馆提交 `ui:turn.submit`）：只收到一条
`turn.delta`（承载答案），没有终止帧，直到摊位改成把结束说出来。因此规则按投递方式定，而不是按协议
定：当 turn 是由事件到达的（信封带 `name`），它的结束是 EMIT 出去的——`ui:turn.done` 或
`ui:turn.error`；直接调用方（iterate/call，参数值形状，没有信封）仍然读终止值，与本记录一致。其余
不变：两种模式仍由调用方选择，结束也不是第二套实现。
