# 0005 — skill 的体是代码，不是 DSL

> **语言：** [English](0005-skill-body-is-code.md)（主） · [中文](0005-skill-body-is-code.zh-CN.md)

**状态：** Accepted（2026-10-26）。裁决：skill 内部的组合用**已有语言**写——steel 或
python——绝不用本项目自己发明的格式。执行路径上有一处未验证（§4：steel 能否求值一段
投递进来的字符串）；那是一个待查项，不是对裁决的反对。
**日期：** 2026-10-26

## 背景

ADR-0004 §3 把走法落成「一次调用一步」：`invoke_skill` 跑第 n 步，下一步需要什么由模型
传，顺序归模型。这很诚实——gravity 里没有任何东西替它发明顺序——但它天生低效：每一步都是
一次往返加一次完整的上下文重读。

去掉往返的形态，是一个**自己编排各步的体**。本记录回答的问题是：这个体**用什么写**。

桌面上有三个候选：

1. **自造 DSL**：为步骤、受管的调用与结果发明一套语法。
2. **JSON**：把组合写成数据——一串步骤带各自的参数。
3. **代码**：用节点本来就承载的语言写一段脚本。

JSON 正是 ADR-0015 §3 现在写进 `steps` 的东西（`[{code_id, note}]`），所以它事实上是第三个
候选，应当被明确否掉，而不是因为惯性留在那里。

## 裁决

**组合就是代码调代码。体是一段已有语言写的脚本；本项目不设计 DSL。**

1. **不自造 DSL，也不拿 JSON 当组合形式。** 本项目自己发明的步骤语言，会走到每一个被发明的
   步骤语言都会走到的地方：一个蹩脚的 lisp 方言、一套手写的求值器、第二套控制流规则，以及
   零工具支持。JSON 是另一种失败：它能表达固定顺序加固定参数，别的都不行——没有条件、没有
   复用、没有错误路径——而真实体达到的体量下它还很啰嗦。两者都是别人拿现有工具没法调试的
   格式。

2. **代码之间的组合仍然是图，而这张图是推导出来的。** 一个体会调用其它 code 节点，那些调用
   **就是**步之间的边。k10r 的图本来就装着 code 节点（ns 35）与 skill 节点（ns 36）。所以
   一个 skill 的边集是**从体里读出来的**——解析出来的，不是手工维护的——而不是另存一份
   JSON 清单，跟它所描述的代码一起漂移。组合型 skill 的图表示和以前是同一张图；变的是真相
   住在哪里：住在体里，边是推导的。

3. **两种语言都可用，谁都不是本项目的「官方语言」。** 选择是逐 skill 的，而且已经能表达
   ——code 行的 `language` 就是 gravity 路由用的那一维（ADR-0004 §3、ADR-0001 §7）。区别
   在于各自付什么代价：

   - **steel** 是同像的（homoiconic）：体可以**当数据读**而不必运行，于是推导边、重写、
     consolidation 分析都很便宜。它跑在节点**嵌入的** steel 运行时上（`effector` 的
     `steel` 载体是 resident-only，没有进程），所以 ADR-0001 §2 对「生成的代码不用嵌入载体」
     的那条否决对它字面成立：体会与节点进程共享环境变量、凭据与挂载的文件系统，而 bwrap
     只覆盖进程形式的载体。
   - **python** 可读，是模型第一次就能写对的语言（体由涌现回路写出来时这很要紧），也是唯一
     同时具备「一次性进程 runner」与「驻留 guest」的语言。把 python 的体当数据读需要解析器
     ——一个子进程里跑 CPython 的 `ast`，或者一个 Rust 解析器——这是真实成本，但有界，而且
     买到的是 steel 白得的同一份推导边。

   这份不对称比从外面看起来小：steel 白得的东西（体本身就是树），python 用一次 `ast` 也
   能拿到；python 白得的东西（进程边界），steel 根本拿不到。

4. **执行到底要求什么——以及唯一那处未知。** runner-mount（ADR-0001）每个 mount 的 source
   是**固定的**，所以 skill 的体必须以调用参数的形式到达，并由 mount 的 runner 求值。这就要
   求语言能求值一段投递进来的字符串：
   - python：能（`exec`），`deploy/runners/runner_py.py` 已证。
   - nu：不能——实测（ADR-0001 §8：`source` 要求解析期常量，nu 0.116 没有 `eval`）。
   - **steel：未验证。** 它的载体在冷启动时加载一次 source，而这棵树里没有任何东西求值运行期
     字符串；`steel-core` 是否提供 eval，是一个待查项。若不提供，steel 的体就无法作为 mount
     参数到达,只能要么给每个 skill 铸一个类型（ADR-0001 §2 否），要么走场馆内进程路径
     （ADR-0001 §3 否）——于是 steel 只剩两种可能：作为体的**书写形式**（执行时是别的东西），
     或者作为节点为自家 booth 承载、但不为 skill 承载的语言。

## 后果

- **`invoke_skill` 不变。** 组合的体是**一步**，于是「一次调用一步」就不再是限制：外面没有
  东西需要排序了。工具面、走法、错误词汇都维持已落地的样子。
- **k10r 的 `steps` JSON 清单是过渡**（ADR-0015 §3），不是终点。终点是一条 code 行装着体，
  步的结构从体推导。在体存在之前，这份清单仍是 `resolve` 回答的、`invoke_skill` 走的东西。
- **本项目任何地方都不授权 DSL 工作**：不写语法、不定步骤词汇、不做 JSON 组合格式、不写
  求值器。
- **节点语言面把 steel 加成组合宿主，要等 §4 的检查结果。** 一个不能求值投递脚本的语言，
  就是其 skill 不能骑 mount 的语言；说成能，正是 ADR-0004 §8 禁止的那种撒谎。
- **沙箱问题现在是一个真决定，不是脚注。** 若要 steel 的体在节点进程内跑，那就是明确接受
  「生成的代码共享一个受信进程」——正是 ADR-0001 §2 针对这类代码否掉的那一件事。把这条试金
  石记在这里，是为了它不要某天被意外发现。

## 开放项

- `steel-core` 会不会求值一段运行期字符串（eval 或等价物）？若不会，本裁决里 steel 那一半
  只是书写形式。
- 推导边在什么时候算：k10r 在声明时（写入即 Introspect），还是在 resolve 时？声明时读起来
  便宜，resolve 时写起来便宜——这正是 code 存储对 `parameters` 已经做过的那笔权衡
  （ADR-0012 §2：形状归生产方）。
- 谁来做 python 的 AST 那一遍：k10r 在声明时，还是节点侧对被投递的体做 introspect？k10r 是
  这张图的持有者，这一点支持放在 k10r。
