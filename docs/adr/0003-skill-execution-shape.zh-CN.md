# 0003 — Skill 的执行形态：代码负责组合，进度是数据

> **语言：** [English](0003-skill-execution-shape.md)（主文档） · [中文](0003-skill-execution-shape.zh-CN.md)

**状态：** Accepted（2026-10-14）。设计裁决：它点到的部件部分已落（常驻 guest 的 ctx 桥、
turn 开头的投影拉取），部分欠着（任务行、分发前的门）。
**日期：** 2026-10-14

## 背景

从图谱里取回来的一个 skill 不是一份脚本。它的步骤会分叉——「点餐」这条分支下面挂着步骤
2、3、4，规则是"2 成立就调 3，否则调 4"；一个步骤本身可能就是一整段子过程；而一件跨多次
工具调用的任务，它的**进度**要活过发起它的那一个 turn。

执行这一半曾有三种形态摆上桌：

- **胶水脚本**：分叉写进一份脚本，由它去调其它脚本（下发的脚本是数据，所以除了"能调到
  兄弟"的那条通道，不需要新机制）；
- **流程引擎**：控制流作为数据携带，由一个 runner 解释；
- **备忘/待办**：每个步骤一行任务，绑在完成它的那次调用上，由代码而不是模型推进。

这三者不是同一个问题的三个答案。前两者说的是**一次调用之内**的控制流；第三者说的是
**跨 turn** 的进度，它存在的理由是用 LLM 的 turn 去推进一件多步任务是慢的。它们需要的
东西基本都在，且已核实：常驻 guest 的 ctx 桥（下发的脚本调到兄弟 mount 并取回值——ADR-0001
的状态段）、okm 里一条关系一行（`link` / `unlink` 一次批写、批删全部 face；行删除走
`Collection::delete`；**没有级联**——成对操作本身就是纪律，okm ADR-0015 §B）、以及 gravity
在 turn 开头本来就做的那次投影拉取。

## 裁决

**RULING——代码是组合的原语，进度是数据，执行历史永不改写图谱的拓扑。**

1. **分叉与步骤逻辑写成胶水脚本，不写流程引擎。** 调用方的代码能表达的分叉不需要第二个
   解释器：脚本以参数形态下发（ADR-0001），经 ctx 去调兄弟步骤，组合关系落在一个地方
   看得见。流程引擎的上限是它自己的词汇表，而代码在已经存在的执行器上是图灵完全的——何况
   模型写代码比写流程 DSL 更好。
2. **胶水必须骑在 `carrier` 为 `induction` 的 mount 上。** ctx 桥是一条通道，而一次性
   `exec` 载具按契约没有通道（一份 JSON 进、一份 JSON 出；没有帧、没有驻留、没有 ctx 桥）。
   于是清单的 `carrier` 这跟轴（ADR-0001 §7）**声明**了哪些 mount 能承载组合出来的操作——
   "这道 mount 能不能跑胶水"是声明出来的一件事，不是猜的。
3. **进度是数据：一个步骤一行任务，绑在完成它的那次调用上。** 这条绑定是**图里的边**，与
   事实同图（既有的 task-graph 裁决：任务顶点 + 它们的 link 边进图；完成态是应用的
   结构化状态，不是记忆管线里的事实——近似检索回答不了枚举问题）。完成是调用点的写入，
   永远不是模型的判断。
4. **分发前的门是代码，且在一次 turn 之内它读内存。** gravity 把该 session 的未完成待办
   **连同它本来就拉的投影一起**取进来；此后 turn 内每一次分发前的检查都是内存读——零 per-call
   往返、路径上没有 LLM。真相留在 k10r，快照每 turn 刷一次：本 turn 里写下的进度对本 turn 之后
   的检查可见，别处发生的变更随下一次投影到达。
5. **执行历史只写数字，永不写拓扑。** 计数与权重是可加、可回退的数据（`tool_invoke_count`
   回写就是计数的落点，Phase 5）；胶水脚本是**会话态产物**（一行数据，不是新的父节点）。把
   一个节点挪到另一个父下面属于**改定义**，所以反复出现的组合是**被提议**升级、由一次受审的
   动作落地——永不自动施加。图谱的边界由使用统计涌现（对"调了什么、结果如何"的聚类）；运行期
   改写边不是这些统计之一，而一份按会话产出的东西一旦被升成结构，就会按"跑过它的会话数"
   累积成结构。这条原则与 Aura 对类型的处置是同一条：涌现数据永不铸结构，因为受审的图谱
   不是运行期的编辑对象。

## 已考虑并否决

- **流程引擎。** 它换来一张可见、可暂停、确定的流程图，代价是把分叉、循环、组合重新表达成
  一套词汇表，其上限就是这个引擎实现了多少——而底下已经有一个能跑代码的执行器。它真正多
  出来的那一条（流程可检查）由裁决 3 的任务行给出：那是可检查的数据，不是第二个解释器。
- **按重复次数自动 re-parent（"这胶水跑过三次了，把这几步挂到它下面"）。** 这是拿执行历史
  去改共享拓扑：图谱的结构是受审的、由统计涌现的，胶水节点按会话产出，于是**第一个发明出
  这套组合的会话**会静默地重定义此后所有读者的图谱。与"涌现数据永不铸类型"同一个否决，
  只是把类型换成边。
- **把门做成 LLM 的一步（"看看哪些任务完成了"）。** 这是把一个概率调用压在一条确定性事实
  上：为一个行的比较付一整轮推理，而且模型漏了它就是 **fail-open**——门恰恰是模型不该
  拥有的那类检查。
- **门的态只留在 turn 内。** turn 本地的待办表丢掉跨 turn、跨会话的真相，而想从记忆面重建
  也不行："绑定的任务是否**全部**完成"是一个枚举问题，近似检索面回答不了（应用状态从不走
  记忆管线）。
- **节点侧 dispatcher 解释步骤（早前已否决，此处再确认）。** 它把载具运行时的会话、池化、
  沙箱在部署件里重做一遍，并把路由搬离调用方——而 skill 的语言与载具在调用方本来就是已知的。
- **给 mount 一个路由/订阅声明**（好让下发的脚本 `ctx.emit` 进 realm 的 MQ 平面、有人
  消费）。mount 是执行者，不是发布者：它没有消费者集合，替它发明一个等于把部署件变成
  图谱参与者——ADR-0001 §5 排除的正是这件事——还顺手开出第二条没人要的进度通道。**不加**
  它的行为是明说且被钉住的：下发脚本的一次 emit 会被接受、到不了任何消费者、落进死信环
  并带 `NoRoute`（ADR-0038 §4——可观测、不静默丢弃；`prism/crates/prism/tests/runner_mount.rs`）。
  进度该走调用的返回值或流式 envelope（ADR-0034 的 iterate），调用方本来就在读那里。

## 后果

- **PLAN Phase 2.6** 是本裁决的落地处：任务行、它们与调用的绑定、以及分发前的门。
- **PLAN Phase 4.6** 增加载具约束：组合出来的操作需要一道 `induction` mount，哪些是则由清单声明。
- **PLAN Phase 5** 的权重回写是计数写入，不是拓扑编辑。
- **okm 侧：** re-parent 是一次显式的 `unlink` + `link` 成对操作——删一个节点行不会顺手清它的边，
  这是设计（okm 的 PLAN 记着对"隐式单侧清理"的否决，含它防的那种 stale-edge 复活）。任何"移动"
  节点的代码要自己拥有这成对的两半。
- **代码身份：** 代码节点是按 id 寻址的一行——没有名字、没有 hash，而这够用，**因为脚本以调用
  参数形态传递、每次调用重新读**（零陈旧窗口由构造保证）。反面情形是 mount 自己的 runner 源码：
  驻留只在冷启动 load 一次，那一份保持内容寻址（ADR-0027 的 blob + ref），因为按 id 寻址的
  驻留源码会静默地一直跑旧代码。
- **仍开：** 任务行的 schema（字段、绑定边的种类、"session" 把门的范围圈到哪）、完成写入归
  gravity 还是归 runner、以及升级路径的形态（问谁、提议带什么证据）。
