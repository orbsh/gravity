# 0017 — 对话记录有预算，轮次自己读数

状态：已接受（2026-11-25）

## 问题

一轮 turn 把手上的 messages 直接发出去，成本要到事后才知道——从 endpoint 的拒绝里知道。由此两件事。其一，记录会无声地长：工具结果原样进 transcript，没有任何东西量过下一次请求要花多少。其二，阶梯计费的 endpoint（本 ADR 是对着它建的：一个请求的 prompt tokens 落在哪一档就按哪一档收，`1M` 窗口里的 `512k` 就是高档的起线）一旦跨线，就按高档收**整个**请求，一次，不给警告，这一轮里也没有第二次机会。

今天唯一的压缩是语义触发，不是测量：当这一轮要派发的工具里有 `human` 性质的调用（可能几分钟不回，它已经读过的 payload 就不值那份字节了），已完成的工具轮才折叠。于是一轮全是 fast 调用的对话可以无限长，直到 endpoint 说不。

## 决定

**窗口是模型的属性，就住在模型那一行。** `models` 加一个冷字段 `context_window`，十进制字符串。缺省（或写坏）等于这个部署没有声明窗口，turn 什么都不感知——就是这个 ADR 之前的行为。它不放 `settings`：一个部署可能同时服务两个窗口不同的模型，而窗口不是部署挑选的策略。

**测量用 endpoint 的数，不用我们的。** 声明了窗口的请求带 `stream_options: {"include_usage": true}`，turn 从流里的 usage 读 `prompt_tokens`。本地 tokenizer 被否掉了：它是对同一个数发表的第二意见，而它在真正要紧的情形里（工具结果、JSON、代码）恰好估不准；账单也是按 endpoint 的数算的。没有声明窗口的部署根本不会去要 usage——不发字段，不付代价，也不去打扰一个比这个字段更老的服务器。

**这个数走解码器，不走事件。** 一个 chunk 可能同时带内容和 `usage`；事件变体只能排在已经就绪的 delta 后面，而这个队列在调用方停止拉取的那一刻就把数丢了。SSE 解码器留住最后见到的 `usage`，在流结束时交出去；done 信封顺带带着它（`{"done": true, "usage": …}`），因为那本就是 turn 在看的轮次边界。

**三条线，每条的理由都不只是"高"。**

| 线 | 动作 | 为什么是这个数 |
|---|---|---|
| 窗口的 `0.5` | 折叠已完成的工具轮（`compact_finished_rounds`） | 它就是 `1M` 里 `512k` 的档位线：跨线按整个请求涨价，所以折叠发生在线上，不是快到顶才发生 |
| `0.8` | 再把最老的历史行裁到最近 `HISTORY_KEEP`（8）条，留一行说明丢了几条 | 尾部才是下一次推理在谈的东西；它上面的摘要块代表更早的一切，而那些行是**存储的**——下一次投影就会把它们交回来 |
| `0.95` | 不发这一轮：写一行说明、带着这行关闭 turn、以那句话失败 | endpoint 会拒的轮次不是轮次；而空回复会被读成 provider 的错 |

判定本身是两个数的纯函数（`budget_of(prompt_tokens, window)`），所以三条边界可以在没有 provider 的测试里被引用。

**它慢一轮，这一点是写明的，不是藏起来的。** `usage` 描述的是刚刚结束的那个请求。所以 turn 用"上一轮站在哪里"决定下一轮的形状，此外不加任何估算。误差就是一轮的工具结果，这也是为什么线都留了余量（0.5 是价格线，不是上限）。

## 这个决定不做什么

- 不做 tokenizer，不引 `tiktoken`，不做字符启发式。endpoint 不报，就什么都不感知。
- 不持久化这个数。写一条 `usage` 行需要 k10r 有一个机器 kind（`mem_core::channel::kind` 只有 TEXT/TOOL_CALL/TOOL_RESULT），为一个诊断量发明一个 kind 是 k10r 的决定，不是这个 booth 的。今天读数只到 stderr，每判定一次一行：`[gravity] context 512340/1000000 (51%) · Compact`。
- 不改变没有声明窗口的部署：wire 不动，每条路径都返回 `Budget::Free`。
