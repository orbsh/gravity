# 0015 —— 上下文（context）是「有人能看着」的工作单位

状态：Proposed（2026-11-21）。本记录描述的机制已经落地：CLI 的 `--context`、booth 的「声明的 agent 身份」规则、`find_member`、`supervise`，以及 smoke 里那条「同一 context 跑两次、第二次看得到第一次」的腿。记录补上的是**一般性的说法** —— 后台任务、并行批次的每一个，都是同一个对象，只是开这一轮的手不同。

## 背景

CLI 是 gravity 自己的门，不是场地的门（ADR-0002）：它经过 prism，因为那是唯一的一条线，但它驱动的是 agent。由此带来一个躲不开的问题，而这个问题的答案决定了其余一切的形状：

**活儿是人交代的、但说话的不该是那个人 —— 那是谁在说？**

第一个答案是显而易见的那一个 —— CLI 以登录者的身份说话，因为场地在每一个页面事件上盖 `sender.user`，而 k10r 的 member id 就是用户的 uuid（k10r ADR-0025）。它错在要紧的地方：一个每晚跑的脚本会把它的行写进那个人自己的线里，与他亲口说的话混在一起；人回到自己的频道，发现一台机器在用他的身份说话。同一种失败会在每一个别的活儿来源上重演 —— 事件触发的任务、并行的批次 —— 每一个都要么借一个人的身份，要么没有身份。

## 决定

**context 是 agent 工作单位：一个名字、一个由名字派生出来的 agent 成员、一条频道、每次调用一轮。**

1. **名字就是身份。** `--context "drift check"` 从名字派生 member id（FNV-1a 两遍，uuid 形状），连同 `member_name` 一起声明给这一轮。于是同一个名字每次运行都是同一个说话人；又因为「一个成员在一条频道里的行」就是它的对话，同名同频道就是同一个 context。两个名字是两个 agent。不需要任何文件保存它们：身份是名字的函数，没有可丢可忘的东西。

2. **进程可以是 agent，永远不能是人。** booth 的规则按顺序是：场地盖了章而调用方没有声明 —— 用章；声明了而 k10r 说那是 AGENT（role 1）—— 用声明；声明了而那是 PERSON —— 不用（用章：客户端不能自称一个它证明不了的身份）；声明了而库里从没见过 —— 按它带来的 `member_name` 登记成 agent；声明了但没有名字 —— 那是调用方自己的兜底 id，照样用章。既没有章也没有声明 —— 拒绝：没有这样的说话人，而一行不点名的人就是在说假话。

3. **给这一轮看什么，由库决定；程序不给转写。**
   决定的位置是 `GET …/members/{m}/session`。读的人是**人**，投影就带记录 —— head、summary、increment；读的人是 **AGENT**（`member_role::AGENT`），投影只带 head，别的什么都不带，它的行留在日志里，作为人打开就能看的监管记录。这个不对称说的是**指令**，不是隐私：人会发出改变当前上下文的指令，而那不可预测，所以模型需要一部分对话记录才跟得上；程序跑的是已知的形状，它要记住的东西靠提交事实、开任务 —— 与人这一轮走的是同一扇门。

   这件事**故意不放在调用处**。谁自己装配提示词，谁就把知识策略复制到每一个调用处（gravity、页面、将来的别的驱动器），各自对「模型该看到什么」有一套看法；而这座库存在的理由 —— 把一个部署学到的东西变成可以发出去的知识 —— 就得在每个调用旁边重写一遍。所以：调用方只渲染投影给它的东西，按投影给的顺序。任何地方都不把知识烤进提示词：哪些事实、哪些技能、多少记录、哪些没做完的活儿进到一轮里，始终是库的决定，逐次读取时决定 —— `owed`（「这段记忆还欠着什么」那一段）就是按这条从 booth 搬进库的，k10r ADR-0021 里已写明。

4. **人的那条线是被点名的，不是猜出来的。** 引擎以前取「这个成员所在的第一个频道」—— 在一个成员只有一条频道时成立，等 agent 能把它工作所在的频道塞进人之后就错了：监管人自己的话会落进机器的线里。哪条频道是某人自己的，由 k10r 记录（`solo`，k10r ADR-0025），引擎按名字去要；从成员派生出来的 id 只是**首次打开**那条线的 id，绝不是回到一条已有线的路径。

5. **每一种活儿来源都是这个形状。** 人的一句指令触发的后台任务、事件触发的引擎、并行批次里的一个条目：每一个都是 context，都以自己的 agent 说话，都用同一套方式被看着。不同的只有「谁开了这一轮」—— 一个人在打字、一个调度器、一次扇出 —— 而这是唯一的不同。开轮的人不是这条线的属性。

6. **监管是数据，不是开关。** k10r 的行写明说话人（k10r ADR-0009 §1），所以混合的线读得出来；频道的成员关系就是可见性集合。谁来监管由 agent 决定 —— `find_member` 按名字问目录，`supervise` 把它选中的人加进频道 —— 因为只有它知道这份活儿是为了什么、谁能对它做出反应。监管人可以有好几个，也可以没有：agent 替自己干的活没有人可以汇报。客户端不携带这个开关；被撤掉的 `--supervisor` 参数就是「客户端侧的名单是错的形状」的证据。

7. **并行工作是一条 context 一条频道。** 两个 context 共用一条频道，各自都会读到对方的行：两个叙述者、一份转写，提示词里混着两件事。线才是隔离的单位，而「看着它」的意思就是「打开它的频道」。

## 后果

- 与一个人的对话和一份后台作业成了同一个对象，只是开轮的手不同 —— 一套实现、同一批门（带 sender 的 append、目录、成员关系）。
- 监管存在库里，成为成员关系，于是它比做出这个选择的进程活得久，并且对每一个读者可见，而不是只对一个客户端可见。
- 场地对人的权威保住了：这里没有任何东西允许一个调用方替别人说话 —— 将来那套 token 机制（PLAN 的 open items）必须保住的性质就是它。
- 这里没有的：名字注册表、context 上的归属记录、以及任何「context 完成了」的概念。context 是一条线，不是一件作业；任务是 k10r 的 task 行，住在部署自己的 scope 里（ADR-0003 §3）。
- context 有记忆的延续，没有**对话**的延续 —— 而且这是投影的性质，不是每个调用方的性质。同一个名字的两次运行是同一个说话人、同一条频道；第二次不会被展示第一次，要记住就提交事实、开任务。把行读回来是人做的事。
