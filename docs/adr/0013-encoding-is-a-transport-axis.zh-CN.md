# 0013 — 编码是传输轴：两种内容模式 × 两种编码

> **语言：** [English](0013-encoding-is-a-transport-axis.md)（主） · [中文](0013-encoding-is-a-transport-axis.zh-CN.md)

**状态：** 已接受（2026-11-19）。它固定一帧的**内容**在出去时如何被编码；它不新增第三种输出模式。
**日期：** 2026-11-19

## 背景

一次 turn 只说两件事之一，由调用参数选定（ADR-0009）：文本，或 accrete 帧。这是**内容**轴，由调用方要什么决定。

紧凑不是一种内容。同一帧就是同一帧，无论它是以文本还是以 CBOR 过链路——变的只是它占多少字节、以及人不借助解码器能不能读。把「CBOR」当成第三个 `protocol` 值正是那个诱人的错误：那会让 JSON 有两种内容模式、CBOR 只有一种，而每一个消费者都会开始按一个与 turn 画了什么毫无关系的区分去分支。

## 决定

**裁决 —— 编码与内容正交：两种内容模式 × 两种编码 = 四种组合，而不是三种输出模式。**

1. **每条腿自己回答，什么都不向下传播。** 编码是**连接**的属性，不是请求的属性，所以在握手时定下，永不随载荷旅行。客户端可以要求 prism 给 `accrete-json` 或 `accrete-cbor`（子协议优先，`?codec=` 是简化入口；缺省即 `json`，无法识别的值是拒绝握手而不是静默回落，`PRISM_CODECS` 可把一个部署钉死为单一编码）。摊位在被启动时声明自己的编码。若必须，prism 在两条腿之间转码。客户端的选择不向下走，摊位的声明也不向上走。

2. **摊位声明自己能说什么。** `Body::Script::encoding`（`json` | `cbor`）在 spawn 时设定，以 `INDUCTION_ENCODING` 到达 guest；gravity 声明 `cbor`。不声明即 `json`——这里猜错不会报错，只会送出乱码，所以安全默认是可读的那个。

3. **客户端腿上 JSON 是缺省，并且保持缺省。** 整个调试故事——fluxen 的 `stage console`、`stage tojson <dump>`、走查——都依赖人能直接读的帧。紧凑按连接选择。

4. **载荷自己说明是哪种，靠形状。** JSON 链路上内容是 `data = {"$cbor": "<CBOR 文档的 base64>"}`：一个保留键，于是接收方无需带外配置就能分辨。CBOR 链路上内容是**真正的 CBOR byte string**——`induction-protocol` 的 `payload` 模块在入口把它分开、在出口重新拼好，于是 `Value` 型读者看到的仍是那个映射，而字节始终是字节。

5. **等价是被测出来的，不是假定的。** 两种编码必须解出**同一个**值：induction-guest 在真实 CBOR 管道上证明（两条 `emit` 路径、同一个内容值），gravity 跨越 guest 边界证明（一帧、两种编码、两边都解），prism 在它唯一的解码漏斗 `ui::decode_content` 处证明。只断言「能解析」会掩盖悄悄改变了值的编码器；断言相等则掩盖不了。

## 实测

同一组十帧，本机（2026-11-19），由 gravity 的 `the_four_payload_sizes` 测得：

| 拼写形式 | 字节 |
|---|---|
| 美化 JSON | 18 257 |
| 紧凑 JSON | 6 182 |
| `{"$cbor": base64}`（帧到达 aura 的 realm 接缝时的样子） | 6 168 |
| 带字节串的裸 CBOR（帧在管道上的样子） | 4 618 |

这张表给出两个答案，两个都需要。二进制比紧凑 JSON 省 **25%**——但只在字节保持是字节的地方成立。在 realm 接缝处，`Handler = Fn(&Ctx, Value)` 逼出一个 `serde_json::Value`，同一帧到达时是 6 168 B，相对朴素 JSON 只省 1.3%，单凭这一点不值得第二套编码路径。

## 后果

- **「端到端二进制」目前不成立，记录里写清它停在哪。** `Value` 型分发载荷（`HostFn`、`Realm::emit`、`aura_booth::Handler`）把字节拼回 base64；去掉它属于改 aura 的载荷类型，而不是改编码。在那之前，字节路径在管道上有收益，在接缝处被洗平。
- **管道编码与内容编码相互独立。** 切换一个不切换另一个，而 JSON 链路照样正确承载 `$cbor` 载荷——这正是「轴」在这里的意思。
- **CBOR 模式的帧不能靠眼睛看。** 调试它的运维先解码；帧转储测试就是这么做的（`GRAVITY_FRAMES_OUT` 在 CBOR 模式下转储，解成 JSON，原样交给 `stage tojson`）。
- **接收方永久兼容两种形状。** 没有版本标记：JSON 链路上标记在不在就是判别器，而一个删掉该分支的接收方会静默地什么都画不出来，这一点相等测试会抓住。
- **新增内容模式仍然便宜。** 第三种模式只多一个 `emit` 调用点，而不是一张编码矩阵：漏斗已经替它们所有人回答过一次编码问题。
- **协商按连接发生，所以一个部署不会混用。** 一条连接上两种编码就是一条坏连接，所以选择落在握手处而不是每条消息。
