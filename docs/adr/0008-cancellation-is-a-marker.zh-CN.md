# 0008 — 取消是 turn 自己检查的标记，不是 kill

> **语言：** [English](0008-cancellation-is-a-marker.md)（主） · [中文](0008-cancellation-is-a-marker.zh-CN.md)

**状态：** 已接受（2026-10-30）。原则与边界规则已决定；「标记放在哪，才能让一个**正忙**的 turn 看见它」记为欠账。
**日期：** 2026-10-30

## 背景

一次 turn 不是一个原子行为。它开一条 provider 流、读 token、在两次推理之间跑工具调用，直到最后才 append 这一问一答。用户中途改主意时没有可寻址的对象：今天 prism 的 `turn_cancel` 是 dispose 一条 iterate 流，而 pull 面已经退场（PLAN Phase 4.1 `NO PULL FACE`），没有流可以 dispose。

两个显而易见的答案在这里都是错的。

**杀掉摊位。** 它是要解决的问题的硬的逆操作：realm 握着存储指针，guest 握着旁路与已收 token，进程在 turn 中途消失，会给 k10r 留下一个未闭合的压缩节点和一次没有 append 的对话。「停止」会变成「丢掉发生过什么的痕迹」。

**发一个 cancel 事件。** 事件平面对同一个实例是一件事一件事投递的，而正在跑 turn 的恰恰就是那个实例：turn 运行期间发出的 `view:turn.cancel` 会排在它后面，在一次本该被它截断的结束之后才被处理。消息无法取消同一个邮箱正在做的工作。

## 决定

**裁决 —— 取消是 turn 自己观察的状态，观察点就是 turn 本来就有边界。**

1. **是标记，不是消息。** 取消写一个标记；turn 读它。什么都不投递，什么都不从外面打断。

2. **检查点落在 turn 已有的边界上**，粒度是**策略**而非常数：流式 chunk 之间（每个 token、每 N 个 token、每轮一次），以及工具轮之间。每个 chunk 检查一次，turn 在一个 token 的延迟内停下；每轮检查一次，则在下一个推理轮停下，代价是那一轮的 token。

3. **函数调用是原子的。** 正在跑的工具调用会跑完，结果被丢弃；mount、脚本、请求内部一律不打断。边界规则正是这一点得以诚实的原因——标记永远不在没有安全点的地方被读。

4. **被取消的 turn 不 append 任何东西，并说明原因。** 最老的规则不变：只有成功的流才 append。调用方在它正在画的那条线上得知这次 turn 结束，原因是取消——不新增事件词汇，也不给消费者一个会被忘记的 `cancelled: true` 字段。

5. **标记按 turn 归属，随 turn 清理。** 活过自己那轮的标记会取消下一轮；调用方忘了清理的标记，就是一次永远不会作答的 turn。

## 欠账部分

**标记存在哪，才能让一个正忙的 turn 仍然看见它**——以及谁有资格写。两种载体都与本裁决相容：

- **场域存储里的一行**（应用自己的 ns，与 ADR-0007 的 settings 并列）。turn 在每个边界读它。写者不可能是 turn 自己的类型——它的实例正忙——所以写必须来自一个能在该实例工作期间抵达那个 ns 的组件（场馆按该类型的 plan 执行一次 store 操作，或一个共享它的第二摊位类型）。这是能力问题，不是词汇问题：谁写谁就必须被授权，而授权不能是 turn 自己的队列。
- **turn 自己队列上的待处理事件数**（`ctx.queue_depth("view:…")`）：标记**就是**一个等待中的事件，turn 读取有多少个在等而不消费它们。没有写路径、没有共享 ns——但它又把 cancel 变成了一条排队消息，只是按**电平**读而不是按**边沿**投递，并把取消绑在场域事件的命名上。

两者都合法；选择属于实现，本记录保留的要求是：无论选哪个，它必须能从运行中的 turn 内部读到、并能从外部写入。

## 已考虑并否决

- **在 realm 层中止激活**（aura 增加 job 取消面）。它是唯一真正的抢占，也是唯一可能给存储留下半次 turn、且没有留下原因的一条。若将来落地，它属于 aura 调度器出于资源原因的处置，永远不作为 gravity 的取消机制。
- **客户端自己停下**（页面不再画、忘掉）。它让模型继续花 token、让 k10r append 一段没人读的对话——正是标记要阻止的状态。
- **用每轮的计时器当取消机制。** 时间不是意图：用户还在看的长回答，不该被自己的时钟切断。

## 后果

- 取消路径变成一个可读的事实：操作者能看到某次 turn 被取消过、什么时候取消的，因为标记是数据，而不是消失掉的信号。
- 部署多一个策略旋钮（`cancel_check_every` 或等价物）。默认：每 chunk 一次——这是流式 UI 期望的行为。
- turn 多一项边界义务：每个流式循环、每次分发都要经过检查；后来新加的、绕过它的循环，就是本记录这一类 bug。要测的单元是「流中途设下标记 → turn 停止且不 append」。
- 取消不是重试：什么都不重跑。用户的下一条消息才是重试。
