# 0002 — CLI 是客户端，不是 REPL

> **语言：** [English](0002-cli-client-form.md)（主文档） · [中文](0002-cli-client-form.zh-CN.md)

**状态：** Accepted（2026-10-14）。只关乎排队顺序；还没有实现。
**日期：** 2026-10-14

## 背景

Gravity 计划中的面是同一个函数的三种驱动：CLI for 循环（本地）、aura 摊位（分布式）、
FaaS 驱动（推迟）。CLI 最初的设定是本地聊天循环——套在 turn 函数外面的一个 REPL。

两件事改变了答案。

其一，ADR-0001 把执行整个搬离了本地进程：gravity 不持有执行面，所以 CLI 想做什么都得
像其他客户端一样提交给场域。仍然"本地"的只是记忆服务与节点恰好跑在哪台机器上——那是
部署事实，不是第二种驱动。

其二，产品面。Web 前端是人在对话里的主界面；终端 REPL 会是同一套交互会话（提示状态、
流式渲染、取消语义）的第二份实现，渲染面还更差。终端真正比浏览器强的地方恰好是对话的
反面：组合、批处理、脚本化——而这正是 REPL 最弱的（每次调用都带交互状态、人的节奏、
输出是为眼睛而不是为管道塑形的）。

## 裁决

**RULING — CLI 是场域的客户端，按自动化塑形。**

1. **一张协议面。** CLI 是 prism 的 WS 客户端，说既有的 turn 动词（`turn.submit` /
   `turn.cancel`，delta 流到 `turn.done` / `turn.error`）。没有第二套 RPC 面，没有
   CLI 专属端点——"接口是 WS，CLI 包装 WS"是既有裁决，本记录沿用它。
2. **kubectl 形态，不是 REPL 形态。** 一条命令 = 一次调用；stdin/stdout；有意义的
   退出码；脚本默认拿机器可读输出、终端拿可读渲染；批输入是一等公民（一串文件、一个
   通配、一条管道）——"把这二十个文件读一遍然后告诉我它们在说什么"正是 CLI 存在的
   理由。
3. **没有交互会话状态。** 没有 REPL、没有本地对话循环、没有"提示—等待"。会话连续性
   属于 channel（k10r），不属于终端——两次调用之间客户端不需要持有任何东西。
4. **优先级低于 Web 前端。** Web 是人的界面，CLI 是自动化的界面。开发顺序照此排队，
   CLI 不阻塞服务 Web 的那些相位。

## 已考虑并否决

- **REPL。** 它把 Web 客户端的"有状态"复制到第二个地方，每次调用都带自动化用不上的
  交互状态，还会把 ADR-0001 刚拆掉的"第二种驱动"分叉重新造出来。REPL 是一个 UI 选择，
  客户端形态的命令将来若真值这个价，可以再长出交互模式；反过来（从 REPL 起步）会让
  协议面围着它塑形。
- **本地 CLI 驱动（gravity 进程内、直连记忆服务）。** 对任何要执行的东西，这正是
  ADR-0001 排除的形态；对其余部分，它也是通往同三个调用（取会话、推理、append）的
  第二条路——而那三个调用场域已经拥有。
- **CLI 专属协议（更精简的行协议、一个 HTTP 端点）。** 第二张面意味着两条鉴权路径、
  两种流形态、两种失败形态。既有动词已经覆盖提交、流式与取消。

## 后果

- **`docs/PLAN.md` Phase 6** 改述为本裁决："CLI over Prism WS"仍是内容；"本地 CLI
  直连 Krystallizer"这一读法退役——本地有记忆服务是部署事实（`store_url` 随调用走），
  不是第二种驱动。
- **"三种驱动"的说法收成一**：一种执行形态（一次摊位激活）加上若干客户端。推迟清单里
  的 FaaS 驱动在原则上不受影响——turn 仍然是函数，只有它的工具执行需要场域，而函数
  可以经网络触达场域——等真正拾起时再议。
- **没有协议工作。** `turn.submit` / `turn.delta` / `turn.done` / `turn.error` /
  `turn.cancel` 都已存在且被测试覆盖（prism 的 `turns.rs` + `turn_e2e.rs`）；
  CLI 增加的是一个客户端，不是一张面。
- **仍开：** 命令面（动词名与其参数）与输出约定（JSON 形状、流式渲染、退出码映射）
  ——客户端侧设计，对场域无影响。
