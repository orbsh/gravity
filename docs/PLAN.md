# PLAN

Design lives in the wiki (stateless-agent-architecture.md / krystallizer.md) and in this repo's ADRs (`docs/adr/`: 0001 — the execution surface, 0002 — the CLI form, 0003 — the skill execution shape); this file only sequences phases.

## Milestone A — Local turn executor

- [x] Phase 0 — Workspace skeleton: `crates/{core,cli,config}`. One happy-path turn: fetch_session (the projection) → LLM call → append delta. No tools yet; plain chat against Krystallizer.
  LANDED 2026-10-10: `MemorySurface` seam (in-process `ChannelStore` wrap / mem-server `HttpSurface` — ADR-0007 as revised: HTTP is the single cross-process form, in-process is a local detail); config takes `store_path` or `store_url` (store_url wins); turn contract tests run the same assertions through BOTH surfaces against a real mem-server (failed turn appends nothing, one-ts-two-subs delta, checkpoint pruning flows through the seam). Turn body copy in the seam test stands in for the LLM stub until LlmClient grows an injectable transport (Phase 1).
  LANDED 2026-10-20 (k10r's read side moved to rendering — the seam's currency is now the PROJECTION, not storage rows): `fetch_session` returns `SessionProjection { head: String, coverage_ts, summary, increment: Vec<(MessageKey, ViewRow{role: Option<String>, kind, content})> }`. ① The head is TEXT rendered by k10r (initialization memory), injected as the FIRST system block verbatim — gravity assembles nothing about the graph. ② The increment entry is flat and carries the role NAME (k10r's mapping; `None` = an unpoliced code, read as `user`) — the old nested `{key, row:{role u8}}` decode is gone from both `HttpSurface` and the booth's turn guest. ③ The representation is a deployment fact: `memory_format` (config / `GRAVITY_MEMORY_FORMAT` in prism's turn args) sends `?format=`, and `struct` is REFUSED at once (`MemoryFormat::from_config`) because it returns fact data for a caller that assembles the graph — which this executor never does. ④ `InProcessSurface` now wraps `mem_core::ServiceStores` (one database, both keyspaces; channel-then-graph lock order) and renders through the same function, so both surfaces answer byte-identical heads — `head_is_rendered_by_both_surfaces` pins it. Repair cost paid here: both locked okm pins (gravity, prism) sat at revs older than mem-core@k10r HEAD requires; both moved to `bd023aa`.
- [x] Phase 1 — LLM layer: the provider is a SEPARATE booth type, not gravity-internal plumbing (aura ADR-0034; ADR-0031's ruling applied: outbound access lives in a booth's own code). Provider booth = Rust over the induction pipe (`reqwest-eventsource` SSE against OpenAI or any OpenAI-compatible endpoint, parsed into a producer that answers each pull round with an envelope and closes with `done: true`); key custody via env injection, never in the module or args; transport-level retry/backoff lives here. Gravity consumes it through `ctx.iterate(provider_booth, handler, args)` — a native pull loop. Responsibility cut: model selection, fallback, circuit breaking, transcript-aware retry STAY gravity-side ("LLM identity stays Gravity-side" — cache binding, untouched). Local CLI (Milestone A) may call the provider code path in-process during bring-up, but the production shape is booth-over-iterate: the sibling booth is the access method. Prompt-view byte-stability contract test (fetched view prefix must be byte-identical — context-cache correctness depends on it).
  LANDED 2026-10-13 (mostly with Phase 4.1 — the provider guest IS the streaming provider; the phase closes with its residuals): ① the SSE wire decoder has ONE home (`gravity-core llm::sse`, gravity `72886a5`) — the provider guest and any streaming consumer share it, the transport stays with the caller (feed/decode protocol, no reqwest-eventsource needed: the guest is a sync process, `ureq`'s blocking reader IS the pull backpressure). ② transport retry (gravity `931c75b`'s follow-up): constant backoff, 3 attempts on transient failures (connect errors, 5xx); a 4xx fails through on the FIRST attempt — retrying a 401 is just delay. Two contract tests lock both. ③ prompt-view byte-stability (`crates/core/tests/prompt_stability.rs`, 3 tests): same state assembles byte-identical views across BOTH surfaces (in-process and HTTP each own their store — one fjall directory = one process, ADR-0007, so the cross-surface assertion compares the same logical conversation, not the same directory); appended history is a byte prefix of the next prompt (append-only, prefix cache hits ride it); checkpoint compression is the ONE deliberate rewrite (documents the boundary). Residual (recorded, not owed): the CLI's `LlmClient::complete` is still non-streaming blocking — Milestone A's bring-up path, Phase 2's tool loop decides whether it collapses into the streaming face.
- [x] Phase 2 — Tool-call loop: parse LLM tool calls → dispatch to Probe → record tool_call/tool_result into delta → feed back. One mode only; no privileged calls. Delta boundary: only this turn's additions, never a full-session write-back.
  LANDED 2026-10-13 (first cut — gravity `4a82359`; the Start-face dispatch loop and its e2e land in the same day's follow-up batch): gravity-core gains the `tool` module — the OpenAI tool-call shapes with the wire's JSON-string `arguments` decoded ONCE at the boundary (`parse_tool_calls`), `ToolResultMessage`/`ToolDispatch`, and the standing rule that a tool FAILURE is a value into the next inference, never a turn failure. The SSE decoder carries `tool_calls` through the chunk stream as its own event (`SseEvent::ToolCalls`, arguments verbatim — the caller parses); the provider guest forwards them verbatim inside its envelope (the provider is transport, not policy). The turn guest runs the loop on its START face: a `tool_calls`-first reply (no content) is parsed, dispatched through `ctx.invoke(tool_target, "", name, args)` to a SIBLING booth type, the result is appended to the working message list as the OpenAI feed-back pair (assistant call + `role: "tool"`), and the provider is re-opened with it; the results also ride `TOOL_RESULTS`, which the PULL face surfaces first — the consumer sees the loop's progress before the content deltas. The cap is 8 rounds, and a provider still asking for tools when it runs out fails the turn with a named error (never an empty first token, never a stream that opens and then dies on an empty reply). `tool_target` is a DEPLOYMENT fact read from the turn args (default `effector`) — gravity resolves no locations itself (Phase 4.5's target shape). Gates: workspace 23/0 (`tool_call_dispatches_to_the_sibling_booth` dispatches into effector's `induction_loop` fixture registered as a sibling booth type and pins the loop's exactly-one re-open; `a_provider_that_never_stops_asking_for_tools_fails_the_turn` pins the cap and "a failed turn appends nothing"), clippy 0, fmt clean. Test-recipe note (superseded 2026-10-26): `boot()` sets `GRAVITY_TEST_KEY` itself, so the suite asks the machine for nothing. Before that, six of the seven tests failed on any machine that had not exported the variable by hand — and they failed as an EMPTY stream, because a failed guest answers a STRING value (`{done:true, value:"…"}`) and `drain_turn` read `done` alone; the terminal round is checked now, so the failure names its cause instead of reading as "the model said nothing". Residual (2.5's face): the transcript/history split (what the working message list persists at turn end vs what the next inference replays), the tool list's source (targets come from the tool list, never from gravity code), and `tool_call`/`tool_result` delta accounting.
- [ ] Phase 2.5 — Transcript/history split + cold-call declaration: the in-turn tool loop keeps a working transcript in resident memory (calls, errors, retries — what the next LLM inference needs); session history receives only the net effect at turn end (intermediate failures are process, not memory). Every tool declares its execution nature at registration (fast/idempotent vs human-touch/external — declared per tool, static, rides `tool_invoke_count`'s registration info); declared-cold tools trigger the cold path at call time (transcript persist + prune before flush: history takes final state, transcript takes the minimal replay set), everything else stays hot with zero flushes. Gravity never branches on local vs remote — execution location lives in target resolution (user namespace + node alias + capability from the tool list), invoke targets come from the tool list, not from Gravity code.
- [ ] Phase 2.6 — Progress as data (ADR-0003): a multi-step task's progress is ROWS, not prose the model advances — one task row per step, bound (edge) to the call that completes it, so completion is written at the call site. Truth lives in k10r as structured application state (an enumeration question the approximate memory face cannot answer); gravity pulls the session's open todos WITH the turn-start projection it already fetches, so every pre-dispatch check inside a turn is a memory read — zero per-call round trips, no LLM on the gate's path. Branch/step logic is a GLUE SCRIPT (code composes; the flow-engine form is rejected), and glue can only ride a mount whose carrier is `induction` (Phase 4.6's manifest states which mounts those are). Execution history writes counters, never topology: re-parenting is a definition change, promoted by an audited act and never self-applied (Phase 5's weight write-back is the counter's home).
- [ ] Phase 3 — Compression as a parallel side branch: when the Krystallizer's fetched view carries a compression marker (watermark reached), Gravity fires TWO concurrent requests from the same immutable prefix — main branch `[H] + [U_n]` answers the user (critical path, normal streaming), side branch `[H] + [compression instruction]` produces the summary. Prefix KV is shared (same-prompt fork — inference servers natively reuse concurrent prefix requests); the side branch pays only its delta. Summary lands before U_{n+1}: the session swaps to `[S] + [recent tail]` at the typing gap — zero user-perceived latency, no mixed-turn. Idle/no-turn triggers (cache TTL cooldown): the side branch is fired standalone (CLI idle tick / Prism timer / Aura `@cron` booth) — off every critical path, pure cost decision. Memory-tool extraction runs on the same branch pattern (past-oriented read branch, output to external state). **Seam half LANDED 2026-10-20:** `SessionProjection.compress` carries k10r's verdict through BOTH surfaces (the in-process one runs the same engine, so they agree), and the checkpoint door now takes the SUMMARY only — k10r derives the coverage point from the verdict it served. What is left is this phase's turn-loop half: firing the side branch and handing the text back.
  TURN-LOOP HALF LANDED 2026-10-26: the turn guest opens the branch from the verdict it was served — the SAME prefix (head + summary + history, without this turn's message) with k10r's `prompt` appended — on its OWN provider instance key (`compress`), because a provider guest holds one SSE connection per process and the realm keys instances by (type, key), so a second stream on the main instance would fight the answer for that slot. The pull face advances both streams round by round (the summary is produced beside the answer, never in front of it), and the terminal round POSTs `{summary}` to the checkpoint door; the coverage point stays k10r's to derive. Failures are swallowed BY DESIGN: a branch that cannot open, pulls an error, or yields nothing leaves k10r's open node as its "compressing" marker (the state the engine already skips) and the turn goes on — maintenance must never cost the user an answer. One RULING taken here: a branch still live when the answer ends is DRAINED before `done` (cap 64 pulls), because the carrier releases the turn's stream at `done` and the guest's state goes with it; the cost is the summary's tail on the turn's end, and the no-wait shape is exactly the scheduled/idle trigger this phase already names below. That trigger and the memory-tool extraction branch stay open. Gates: gravity 25/0 — `the_compression_branch_lands_the_served_summary` streams the answer from one stub (which answers the branch differently, keyed on the tail prompt in the request) and then reads the session back: `summary == "compressed span"` and `coverage_ts == 2000`, the split k10r proposed; clippy 0.

## Milestone B — Distributed execution

- [ ] Phase 4 — Aura Booth binding (`crates/booth`): the same execution function registered as a Booth type; one turn event = one execution. CLI becomes a for-loop over the same function; Booth is its single call.
  LANDED 2026-10-10 (second cut — the turn is FULLY in the booth, streaming end to end): two python booths — the provider (`httpx.stream` SSE → generator, `yield` per token, key custody via `key_env` name, the value never in the module or args) and the turn (`turn` handler is a GENERATOR: fetch the projection from mem-server over HTTP → assemble the prompt → `ctx.iterate` the provider yielding each token straight through → append the one-ts-two-subs exchange AFTER the stream ends). The streaming residual is CLOSED by this cut: per-token deltas cross as envelope items while the stream is live — prism's `turn.delta` contract rides it unchanged. Booths hold no connection state: store_url/endpoint/model/key_env ride the turn args (deployment facts the caller supplies per call). Test recipe then: `PYTHONPATH=<nix-python lib-dynload>:<site-packages> RUSTFLAGS="-L <nix-python libdir>" cargo test -p gravity-booth --features python`.
  SUPERSEDED 2026-10-13 (carrier ruling — gravity is a pure-Rust project; no embedded interpreter): the python carrier cut is retired. Both booths are Rust guest processes speaking the induction pipe protocol (`~/world/induction`; frame vocabulary per ADR-0034's `{item, done}` envelope — single-call and stream share the one envelope shape, `done: true` closes the boundary). The turn booth is an `induction-guest` binary: streaming state lives in the guest process (the process IS the stream state — the old "Rust body carries no stream state" note named the in-process `Body::Rust` closure arm, whose only limitation is lacking resident state to hold an iterator; a resident child process has exactly that). The provider booth is likewise an induction guest (SSE → envelope per pull round). `crates/booth` registers both via `BoothType` process spec (`language = "induction"`), same interface_schema contract (auth block on `turn`), same envelope semantics over the wire — prism's `turn.delta` contract unchanged.
- [x] Phase 4.1 — Re-land the booth crate on induction-guest (supersedes the python cut above): two guest binaries (`gravity-turn`, `gravity-provider`) + registration; the provider's SSE parse stands in for the real endpoint first (fixture stream), then wire OpenAI SSE in Phase 1.
  LANDED 2026-10-13 (gravity `34dd5e5` + `72886a5` + `08ec0c3`; induction `1358e64` + `0c3ab86`; prism `3ccb070`): both guests speak the induction pipe (CBOR codec — the self-delimited document form skips the per-frame JSON quoting overhead). Each guest has a Start handler `.on(name)` (the realm addresses the stream by the handler name — `stream` / `turn`) plus the reserved `.producer()` pull face; a plain `.producer()`-only guest never opens (the Start falls into "no such handler" → terminal-wrapped error → no stream). The turn's stream IS the turn: Start fetches the projection, opens the provider stream through the guest Ctx's NEW iterate consumer arms (`ctx.iterate_start/next/dispose` — the induction face of ADR-0034's pull loop, closing the Phase 4.21 residual), re-emits deltas, and the terminal round appends the one-ts-two-subs exchange (turn args captured in process state — the pull handler only sees the guard's `{stream_id, round}`). The SSE wire decoder has ONE home (`gravity-core llm::sse`, feed/decode protocol; the provider guest and any streaming consumer share it). The turn declares `.auth({turn:true})` — the induction schema's auth pass-through restores prism's gate (fail-open without it, found by turn_e2e). Spawn specs overridable per deployment (`GRAVITY_PROVIDER_BIN`/`GRAVITY_TURN_BIN` — prism's turn_e2e points at gravity's workspace build). prism's `register_executor` delegates to `gravity_booth::register` (no carrier feature gate, no PYTHONHOME/PYTHONPATH for this plane).
  Gates: gravity 3/0 booth contract tests (streaming round trip, append after done, failed provider appends nothing) + workspace 10/0, clippy 0, **no python in gravity's own graph**; induction 33/0 + clippy 0 (auth pass-through); prism turn_e2e 5/5 (auth gate, streaming, cancel, duplicate-submit refusal).
- [ ] Phase 4.5 — Unified call model adoption: tool calls go through `ctx.invoke()` (Aura CallSlot) — target = user namespace + node alias + capability (e.g. `probe:home-pc:read_file`); two-tier waiting handled by the runtime behind one `await` per call-site (hot: park on oneshot; cold: entry-split — no park, transcript flush, task ends, re-entry on result). Retention-window residency: executor stays in memory between calls/turns of the same session, session persisted at turn end or expiry; crash within window rebuilds from event stream. Multi-machine orchestration (e.g. "send the file from home PC to office PC") = two invokes composed in the turn loop — no remote/local branching in Gravity code.
- [ ] Phase 4.6 — The execution surface is the runner mount (ADR-0001): every machine (the control plane's included) runs an effector node; each (node alias × operation language) gets ONE `RemoteProbe` mount whose source is a fixed deployment artifact (a runner: interpreter or dispatcher, installed with the node and declared in its manifest); the LLM-selected operation's script is fetched from k10r by gravity and travels as a call ARGUMENT (`invoke(mount, key, entry, args{code, args})`), so a skill — or a skill version — never mints a type, a ns, a route, or a definition row. Work: prism's mount-registration face (node manifest → idempotent registration per boot — `RemoteProbe` definitions are not persisted; the dial-in `Frame::Register` already supplies alias + carriers), the runner artifact + node manifest, and gravity's run call plus the fixed tool list (skill search + run). aura and effector: NO change (existing surfaces; the runner is a definition per ADR-0027, the script is an argument, so there is no per-call code form and no errata). Forecloses: gravity running standalone with execution ability; any local privileged execution path. Node language surface: nu (systems) + python (business logic) are the required installs — steel is in-binary; no shell carrier and no bash fallback (OS operations route to nu mounts); one runner per language, entry `execute`. A COMPOSED operation (a glue script that encodes a branch and calls sibling steps — ADR-0003) can only ride a mount whose carrier is `induction`: the one-shot `exec` carrier has no channel (one JSON in, one out; no frames, no ctx bridge), so the manifest's `carrier` axis is what states which mounts can host glue.
  LANDED 2026-10-14 (prism `d6d385f` + uncommitted work tree; effector `7e06a0f` + uncommitted work tree): the mount-registration face (`prism/src/mounts.rs` — `MountDecl`/`PRISM_MOUNTS`/`register_all`, replayed at boot because `RemoteProbe` definitions do not persist; a declaration now names BOTH axes — `carrier` for the node facility the call runs in, `language` for the operation language a skill is matched on — so the route to a mount is a match, not a name sniff) + the three runner artifacts (`effector/deploy/runners/runner_nu.nu`, `runner_py.py`, `runner_py_guest.py`) + the **ctx bridge OUT of a remote induction guest**, proven end to end: a delivered script calls a sibling mount through the host realm and gets its value back, on a session that has already served two calls (`prism/crates/prism/tests/runner_mount.rs`). Three located breaks were fixed to get there, one per layer: ① the guest's protocol frames rode `sys.stdout`, which the delivered-script wrapper redirects into the result capture buffer — the frame landed in the capture buffer and the call deadlocked to its deadline (the wire fds are now pinned at import); ② a resident session kept the bridge of its cold-start call, so later calls carried a call id nobody was waiting on (the bridge is per-call data: `ResidentSession::set_host`, re-armed by the dispatch seam on every call); ③ the dial-in reader loop resolved host calls inline and parked on a hot realm call whose Result frame only that loop can read — a self-deadlock whenever the ctx target lives on the same node (the resolution is now spawned; both dial-in homes, `prism/src/effectors.rs` and `aura crates/engine/src/effectors.rs`). Still open in this phase: gravity's `run` call (k10r has no script read-outlet yet, and dynamic code needs the language-default ruling). The node's containment half of the manifest has since been carried on the effector side (2026-10-14, effector ADR-0001): the jail is built from the node's own `CapabilitySurface` (`fs_scope` = write scope, `deny_read`, `cwd`), `config.sandbox` is the switch, and a claim with no enforcement point fails the startup — domain allowlists, seccomp and a `command_exec` grant stay unwired.
- [ ] Phase 5 — Skill pull-through: on each tool call, fetch skill spec from Krystallizer via the pull-through path (Probe → Gravity → Krystallizer, never direct); view processing + `tool_invoke_count` weight write-back at this data gate. The write-back is a COUNTER (data, additive and reversible); no execution path rewrites the graph's topology — a recurring composition is proposed for promotion, never self-parented (ADR-0003 §5).
- [x] Phase 6 — CLI over Prism WS (ADR-0002): the CLI is a client of the venue speaking the existing turn verbs — kubectl-shaped (one command = one call, stdin/stdout, meaningful exit codes, machine-readable output, batch input first-class), no REPL, no local session state, no second driver ("local CLI direct to Krystallizer" is retired: a local memory store is a deployment fact). Priority sits BELOW the web front end — the CLI is the automation interface, the web is the human one.
  LANDED 2026-10-26: `crates/cli` is a WS client of prism and nothing else — no `gravity-core` dependency, so the local for-loop is gone with it (the turn function's ONE home is the booth; `gravity-core::turn` stays as the reference implementation the booth's contract tests ride). It sends `login` and falls back to `signup` once (a fresh venue has no account; the password is the same secret either way), then `turn.submit` per positional argument (`-` reads stdin as ONE turn), streams `turn.delta`…`turn.done`, and maps the four failure classes to ADR-0002's exit codes: 0 done, 2 usage/config, 3 auth, 4 turn failed, 5 venue unreachable. Ctrl-C and `--cancel-after-ms` both send `turn.cancel` — the venue's own verb — instead of leaving a turn running behind a dead socket. Deployment facts ride a new `venue { url, username, password_env }` config node (the password in the env var that field NAMES); the LLM fields became optional because a client config has no endpoint of its own. Residual, narrowed 2026-10-26: the CLI has been driven against a stub venue (its own test) and prism's `turn_e2e` covers the real server side; the gap between those two — the SHIPPED binary on a SHIPPED gateway — is now `scripts/smoke-venue.sh`, which boots a stub provider, k10r's mem-server, prism and the CLI, then asserts both the reply on stdout and the message pair k10r recorded (`["hi", "hello world"]`, read back over the HTTP door). It closes the "does the built thing work" question; what stays open is running it as a GATE: it needs the three repos built and three fixed ports, which no `cargo test` can assume, so CI wiring is still named-work. Gates: gravity 30/0 (5 new CLI tests: two turns from two arguments, exit 3/4/5, the cancel verb), clippy 0 for the touched crates.

Deferred gates:

- FaaS driver: same execution function on serverless platforms — only after the Aura Booth path is stable; no new code, just another driver of the function.
- Multi-model routing: model selection per turn/session — after the single-model path is proven; LLM identity stays Gravity-side (cache binding), Krystallizer never learns it.
